# 用对话控制收藏转发

适用已安装本项目、用户希望通过 agent 进行日常控制的场景。程序本身不解析自然语言，也不需要模型持续在线。agent 将用户意图映射到确定命令，后续页面调用同一 Control 服务。

## 先确定正在控制哪条订阅

- 使用已知的配置文件绝对路径：`bili-fav-relay --config /绝对路径/config.json <命令>`。
- 不确定路径时先查当前项目配置与上下文；若确有多个候选，让用户选订阅，不擅自给多个群发送。
- 先读 `status` 和 `schedule`。这两条不发外部请求，不需要机器人密钥。
- 用户举例、讨论功能或查看状态，不代表授权立刻同步。明确要求同步时，才调用 `sync`。
- 凭据由用户通过本地向导保存到系统凭据库，或在自己的运行环境中设置。不要要求用户把 AppSecret、Cookie 发到聊天里，不回显环境变量，不自动复制其他项目凭据。首次部署先读 `docs/deployment.md`，使用 `setup` 与只读 `setup-status`。

## 话语到操作

下表省略 `--config`，执行时应保留确切配置路径。

| 用户话语 | 命令和行为 |
| --- | --- |
| 每 10 秒同步 | `schedule --seconds 10`；保持当前模式，说明短间隔会增加平台请求量 |
| 每 10 分钟同步 | `schedule --minutes 10`；保持当前模式 |
| 把同步间隔缩短一点 | 先查看当前间隔，再取低于当前值的最近一档：60、30、15、10、5、1 分钟、30 秒、10 秒；按 `interval_seconds` 比较，告知改前改后。已为 10 秒则解释下限，不绕过 |
| 改成手动同步 | `schedule --mode manual`；当前一条结束后停止自动处理，不删除待发队列 |
| 现在同步新增收藏 | `sync`；仅本次任务，不切回自动模式、不补发历史 |
| 改成手动，并同步一次 | 先 `schedule --mode manual`，再 `sync` |
| 恢复每 15 分钟自动同步 | `schedule --mode auto --minutes 15`；说明是否还需启动 worker |
| 取消这次同步 | `sync --cancel`；当前一条可结束，保留未发送队列 |
| 暂停所有同步 | `schedule --mode manual`，再 `sync --cancel`；已发出的请求不能撤回 |
| 看看同步到哪了 | `status`；只读，不偷偷启动任务 |
| 启动投石机 / 启动收藏转发 | `start`；后台启动并等待状态握手，重复启动复用现有进程 |
| 退出后台程序 | `stop`，随后查看 `status.runtime` 确认实际退出 |

如果转发未开启、绑定缺失或暂停原因未解除，说明具体阻塞。调整间隔/模式不等于允许开启发送；不要自动改 `send_enabled`，不要自动 `resume`，也不要清空去重表。已明确完成绑定并授权发送的用户不必每次重新确认目标群。

## 准确解释结果

- `queued` / `pending`：任务已提交，尚未完成。命令退出码 0 只说明提交成功。
- `waiting`：正在冷却，按 `next_action_at` 换算用户时区，告诉用户预计何时继续；不可写成没有新增。
- 用户反馈“10 秒设置后却要等待数分钟”时，先核对 `interval_seconds` 与 `poll_error`。`favorite_changed` 表示本轮分页前后不一致，不等于确认被平台限流；设置已保存也仍需遵守失败退避，不重启、不清除记录来提前请求。
- `running`：按 `total` 和 `counts.sent` 描述本次进度。不要把历史累计 sent 当作本次数量。
- `completed`：读取本次 `sync.scan` / `sync.counts`。首次基线应说“已记录已有收藏，之后只转发新增”；空队列说“没有新增待发视频”；有 sent 说“QQ 接口确认发送 N 条”，不要冒称用户实际看到了。
- `failed` / `blocked`：本次未全部完成，说明 `counts` 中已发/待发/失败数量。`uncertain` 必须让用户核对群，不盲目重试。
- `cancel_requested`：取消已提交，当前一条可能仍在处理；`cancelled` 才是任务已停止。
- 模式/间隔保存成功不代表 worker 已启动。不重复启动两个 worker；冷却等待期间也不重启程序试图绕过。

已有 worker 时 `sync` 返回任务 ID，稍后用 `status` 查看。无 worker 时命令在前台执行（可能等待冷却），使用工具的长任务会话保留进程并报告进展。不要用短超时杀掉执行中的任务后立刻重试；若需要取消，用 `sync --cancel` 或前台 Ctrl+C。

## 能力边界

默认自动扫描 15 分钟，最短 10 秒；同一实例的显式同步请求合并。手动批次默认投递间隔 10 秒，第一次扫描只建基线。任务只包含扫描时的待发集合，之后新增留到下一次。

支持本地 CLI、网页部署向导与独立后台启停；没有内置自然语言聊天窗口、MCP 服务或自动开机服务安装。“从指令时间开始”的临时会话尚未实现。不要向用户宣称这些已存在。

间隔接受 10–86400 整数秒；`--seconds` 与 `--minutes` 互斥。`schedule` 默认只改间隔，不代替开启自动模式或启动 worker。以 `interval_seconds` 解读实际间隔；分钟兼容字段可能为小数。10 秒未做真实平台高频验收，不宣称安全或准时送达。失败退避仍独立保留，首次源访问失败至少等 10 分钟；风控暂停仍需用户处理后恢复。

QQ 主动发言权限：当 `control.delivery_problem.code` 为 `40034105` 且任务为 `failed`，提示用户到目标 QQ 群开启机器人的“主动发言”权限，必要时请群主或管理员操作。明确拒绝不需要走“猜是否已收到”的流程。用户确认已开启并授权重试后，先停止后台并确认停止，再 `retry <BV号>` → `resume` → `sync`，必要时重新 `start`；不要通过反复同步试探权限，不自动解除其他未处理的暂停。旧任务若仍为 `uncertain`，保持原有人工核对流程。
